SessionDock 3.0.0

HandleScope built into SessionDock

- HandleScope 0.3.0 is now compiled into the inspectable SessionDock.HandleScope.dll component in the same SessionDock package. Enable the integration and SessionDock starts the worker itself; there is no separate HandleScope download, installer, setup script, or PowerShell execution-policy step.
- The worker is owned by the exact SessionDock process that started it and exits with that process. It runs only as the same standard user in the same interactive Windows session, binds to IPv4 loopback on an ephemeral port, uses a fresh in-memory bearer token, and keeps the reviewed single-use HandleScope plan and Roblox executable checks.
- Existing handlescope.json opt-ins, standalone Automatic/Keep installed/exact-version preferences, and automatic/v1/v2 API preferences remain compatible. A stale exact pin can be changed in the panel without any download or install. A separately installed, signed-catalog-supported HandleScope runtime can still be used as a backwards-compatible external option, while the built-in component is the simple default.
- The standalone-only Refresh reviewed versions action fetches and verifies only the latest signed compatibility catalog, preserves the current selection, and never downloads a HandleScope package or changes either runtime's lifecycle.
- HandleScope remains independently available from its own repository. SessionDock pins the bundled source to the reviewed HandleScope 0.3.0 tag and exact commit, verifies every vendored source hash offline, records that identity in the release SBOM, and ships no separate HandleScope application or installer.

Faster, steadier macro sessions on laptops

- Verified Roblox process leases now persist through playback and reuse trusted identity results. Path-and-process-token proof refreshes on a five-second per-target schedule, while retained-process liveness and exact HWND ownership remain checked beside every dispatch.
- ExactWheel’s stall-resilient scheduler preserves clicks, keys, drags, and hold timing after CPU delays, while coalescing only redundant overdue pointer moves.
- Bounded macro and coordinate caches avoid repeated file loading and transformations without unbounded memory growth. Monitor and DPI information refreshes during long-running playback so scaling stays current.
- SessionDock performs less UI and window polling. When safe, its hidden idle WebView is suspended through a bounded, cancellation-aware path and is reliably resumed for browser work, Stop, or shutdown.
- The second optimization pass removes per-event native-array allocation and repeated timeline sorting. Recordings grow in small pooled segments instead of reserving 500,000 events up front. One playback session and its Windows wait handles are reused across clients, and the timing loop stays off the shared .NET thread pool.
- One low-level physical-input hook is retained for the complete macro run instead of being recreated for every client or loop. Its initial tracked key/button baseline eliminates repeated full native key-state scans, including for very short one-client macros.
- Controller readiness reads metadata only; Play performs the authoritative artifact and exact-target validation. Source events are stored once and tiny per-window coordinate plans map only events that are actually dispatched. Memory therefore grows with macro events plus clients, not macro events multiplied by clients; deterministic coverage includes 1, 8, 32, 100, and 128 clients.
- Playback orchestration runs off the WPF UI thread and progress is coalesced to at most four updates per second. Transient outages use a 250-millisecond-to-five-second base backoff instead of stopping or scanning every 10 milliseconds. Eight-client wave spacing can add at most 850 milliseconds for 128 clients plus the whole-layout target; while healthy targets continue, deferred targets add only lightweight O(n) deadline checks per completed cycle. Sticky failed leases are replaced when due, including whole-layout lease and focus retries.
- Within each discovery, layout, or playback operation, clients using the same canonical Roblox path share one forced Authenticode proof instead of repeating it per client. SHA-256, WinVerifyTrust, and signer extraction use the same open file handle; changed content, retained-process liveness, exact HWND ownership, and dispatch authorization still fail closed.
- Target-window, geometry, process-name, window-class, source-macro, and coordinate-plan cache hits are allocation-free. Foreground assignment polling takes one window snapshot instead of scanning every client, and a slow WebView suspension continues in the background until browser work revokes it.
